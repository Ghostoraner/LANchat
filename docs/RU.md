## 1. Обзор

LANChat — это чат, рассчитанный на работу целиком внутри доверенной локальной сети: дома, в офисе, на LAN-пати — без какой-либо зависимости от внешних сервисов, облачных аккаунтов или интернета. Один компьютер поднимает сервер, остальные находят его автоматически через UDP-рассылку и подключаются по TCP-сокету, зашифрованному TLS.

Главная особенность проекта — он поставляется сразу в виде **двух независимых, полностью совместимых друг с другом GUI-клиентов**:

| | `LANChat.Client` | `lanchat-tauri` |
|---|---|---|
| Стек | C# / .NET 10 / Avalonia UI | Rust (Tauri 2) + HTML/CSS/JS |
| Внешний вид | Классический десктопный тулкит | Веб-интерфейс в стиле Discord |
| Платформы | Windows, Linux | Windows, Linux, macOS |
| Статус | Стабильный | Активно дорабатывается |

Оба клиента общаются с одним и тем же процессом `LANChat.Server` по абсолютно одинаковому построчному JSON-протоколу поверх TLS и могут свободно смешиваться в одной комнате — переписка между двумя разными реализациями клиента работает точно так же, как между двумя копиями одной и той же.

## 2. Возможности

**Сетевое ядро**
- TCP-сервер с полной изоляцией клиентов друг от друга
- Шифрование TLS 1.2/1.3 с динамически генерируемым самоподписанным сертификатом
- Автообнаружение сервера в LAN через UDP-рассылку (порт 5001)
- Построчный JSON-протокол, полностью описан в [разделе 5](#5-спецификация-протокола)
- Список подключённых пользователей в реальном времени

**Общение**
- Публичные сообщения и системные уведомления
- История сообщений: сервер хранит последние 50 публичных сообщений в памяти и отдаёт их клиенту сразу после подключения
- Личные сообщения (ЛС) через поле `to`
- Индикатор «печатает…» — с троттлингом на отправке и автосбросом на приёме
- Передача файлов: файл кодируется в base64 и передаётся чанками поверх протокола, на приёмной стороне собирается обратно и сохраняется на диск

**Защита**
- Защита от подделки отправителя: сервер всегда перезаписывает поле `sender` перед рассылкой
- Тайм-ауты чтения/записи на каждом соединении (хендшейк, простой, запись) — защита от slowloris-атак
- Keep-alive на уровне сокета
- Ограничение максимальной длины строки протокола — границы потребления памяти на одно сообщение
- Rate limiting (не чаще 1 обычного сообщения в 500 мс; `typing`/`file_chunk` из-под лимита выведены отдельно, иначе индикатор печати и передача файлов были бы бесполезны)
- Изоляция ошибок по каждому сокету при рассылке — один сбойный клиент не роняет доставку остальным
- Санитизация ников (ограничение длины, вырезание запятых, которые иначе ломают CSV-список онлайн-пользователей)

**Для разработчика**
- `install.sh` (Linux/Termux) / `install.ps1` (Windows) — определяют ОС, ставят .NET SDK, Rust, Node.js и системные зависимости Tauri, затем собирают всё целиком
- `publish.sh` / `publish.ps1` — собирают self-contained однофайловые релизные бинарники сервера и классического клиента (на машине получателя не нужен установленный .NET)
- `npm run build` в `lanchat-tauri` — собирает нативный инсталлятор (`.msi`, `.AppImage`/`.deb`, `.dmg`)

## 3. Архитектура

```
                     ┌──────────────────────────┐
                     │      LANChat.Server       │
                     │  TCP :5000  (TLS 1.2/1.3) │
                     │  UDP :5001  (discovery)   │
                     └─────────────┬──────────────┘
                     TLS + построчный JSON
             ┌───────────────────────┼───────────────────────┐
             │                       │                        │
   ┌─────────▼──────────┐ ┌──────────▼─────────┐  ┌───────────▼─────────┐
   │  LANChat.Client     │ │   lanchat-tauri     │  │   любой клиент,      │
   │  (C# / Avalonia)    │ │  (Rust / Tauri)     │  │   говорящий на том же │
   │                      │ │                     │  │   протоколе            │
   └──────────────────────┘ └─────────────────────┘  └───────────────────────┘
```

### Компоненты сервера

- **`ChatServer`** — принимает TCP-соединения, при старте генерирует самоподписанный TLS-сертификат, передаёт каждый сокет в `ClientConnection`, а также держит UDP-слушатель, отвечающий на запросы автообнаружения.
- **`ClientConnection`** — владеет полным жизненным циклом одного клиента: TLS-хендшейк, регистрация и санитизация ника, основной цикл чтения, разбор строк протокола, rate limiting, все тайм-ауты.
- **`ClientManager`** — потокобезопасный реестр подключённых клиентов по нику, примитив `Broadcast` с изоляцией ошибок по сокетам, адресная доставка для ЛС и файлов, ограниченный по размеру буфер истории в памяти.

### Компоненты клиентов (обе реализации устроены одинаково по смыслу)

- **Сервис соединения** — владеет TCP/TLS-сокетом, путём записи (сериализован через блокировку, чтобы параллельные писатели — например, поток чанков файла — никогда не перемешивались), и фоновым циклом чтения, который прокидывает разобранные сообщения протокола наверх.
- **Слой отображения** — рендерит список сообщений, список пользователей онлайн, индикатор печати и выбор получателя для ЛС; также отвечает за сборку входящих `file_chunk` обратно в целый файл.

## 5. Спецификация протокола

Каждое сообщение протокола — это одна строка JSON, завершённая `\n`, передаваемая поверх TLS-зашифрованного TCP-потока. **Сервер — единственный источник истины**: он всегда перезаписывает поле `sender` (и верхнеуровневый `timestamp`) в каждом сообщении, которое пересылает, так что клиент в принципе не может выдать своё сообщение за чужое.

### 5.1 Общий конверт

```json
{
  "type": "message",
  "sender": "Alice",
  "content": "Привет!",
  "timestamp": "2026-09-30T18:00:00Z",
  "to": null
}
```

| Поле | Тип | Назначение |
|---|---|---|
| `type` | строка | Один из типов сообщений ниже |
| `sender` | строка | Ник отправителя; проставляется сервером при каждой пересылке |
| `content` | строка | Полезная нагрузка — смысл зависит от `type` |
| `timestamp` | строка ISO-8601 | UTC, проставляется сервером при пересылке |
| `to` | строка или `null` | Получатель для ЛС/файлов; пусто/`null` = публичное |

### 5.2 Типы сообщений

| `type` | Направление | Назначение |
|---|---|---|
| `message` | клиент ↔ сервер ↔ все/один | Сообщение чата, публичное или личное |
| `typing` | клиент → сервер → все кроме отправителя | Индикатор печати |
| `file_chunk` | клиент ↔ сервер ↔ все/один | Один чанк файла в base64 |
| `history` | сервер → новый клиент | Снимок недавних публичных сообщений |
| `users` | сервер → все | Список онлайн-пользователей через запятую |
| `system` | сервер → все | Уведомления о входе/выходе/подключении |
| `error` | сервер → один клиент | Отказ (занятый ник, превышение лимита и т.д.) |

**`message`** — публичное, если `to` пусто/`null` (рассылается всем, включая отправителя, и добавляется в историю на сервере); личное, если `to` указано (доставляется только этому получателю, плюс эхо самому отправителю).

**`typing`** — клиентам стоит троттлить отправку (в этом проекте — не чаще раза в 2 секунды) и автоматически сбрасывать индикатор на приёмной стороне после ~3 секунд тишины.

**`file_chunk`** — файлы не помещаются в одну строку протокола, поэтому на стороне клиента они режутся на base64-чанки:

| Доп. поле | Тип | Назначение |
|---|---|---|
| `transferId` | строка | Объединяет все чанки одной передачи (например, UUID) |
| `fileName` | строка | Исходное имя файла |
| `fileSize` | число | Общий размер в байтах |
| `chunkIndex` | число | Индекс этого чанка (с нуля) |
| `totalChunks` | число | Общее число чанков |
| `content` | строка | Base64-данные этого чанка |

Публичная передача (`to` пусто) рассылается всем, **кроме** отправителя — у отправителя файл уже есть, и он показывает своё собственное сообщение «отправлено» локально из исходных данных файла, а не из восстановленной копии. Личная передача уходит только указанному получателю.

**`history`** — отправляется один раз, сразу после регистрации клиента. `content` — это **JSON-массив, закодированный в строку** с прошлыми публичными `message`-сообщениями (строку нужно распарсить ещё раз). На сервере хранятся только публичные сообщения; личные сообщения и файлы не сохраняются вообще, даже временно, дольше момента доставки.

**`users`** — `content` — список ников через запятую, рассылается всем при любом изменении состава.

**`system`** — уведомления о входе/выходе и подтверждение первого подключения.

**`error`** — при получении такого сообщения во время хендшейка клиент обязан считать попытку подключения неудавшейся (см. [раздел 10.4](#104-отсутствие-проверки-ошибки-хендшейка-даёт-клиенту-ложный-успех) — реальный баг, найденный при разработке именно в этом месте).

### 5.3 Последовательность подключения

```
Клиент                                        Сервер
  │ ── TLS-хендшейк ──────────────────────────▶│
  │ ── {"sender":"Alice","content":""} ───────▶│   (строка хендшейка — важен только `sender`)
  │                                             │   валидирует и санитизирует ник
  │◀── {"type":"system","content":"Connected"} │   (или {"type":"error",...} + закрытие, если ник занят)
  │◀── {"type":"users","content":"Alice,Bob"} ─│
  │◀── {"type":"system","content":"...joined"}─│
  │◀── {"type":"history","content":"[...]"} ───│
```

Корректная реализация клиента **обязана** прочитать и проверить первую строку ответа на `type: "error"`, прежде чем объявлять подключение успешным — пропуск этой проверки был реальным багом, найденным в ходе разработки (см. раздел 10.4).

## 6. Установка и настройка

### 6.1 Автоматически (рекомендуется)

```bash
# Linux / Termux
chmod +x install.sh && ./install.sh
```
```powershell
# Windows
.\install.ps1
```

Скрипты определяют ОС/дистрибутив, ставят .NET SDK, Rust (через rustup), Node.js и системные зависимости сборки Tauri (`webkit2gtk`, `gtk3`, `librsvg` и т.д. на Linux), затем собирают сервер, классический клиент и Tauri-клиент.

### 6.2 Требования вручную

| Компонент | Требует |
|---|---|
| `LANChat.Server` | .NET 10 SDK |
| `LANChat.Client` | .NET 10 SDK |
| `lanchat-tauri` | Rust (stable) + Node.js + системные зависимости сборки Tauri |

## 7. Запуск в режиме разработки

```bash
# Сервер
dotnet run --project LANChat.Server

# Классический клиент (Avalonia)
dotnet run --project LANChat.Client

# Discord-style клиент (Tauri), окно разработки
cd lanchat-tauri
npm install
npm run dev
```

Все три можно запускать на одной машине для локального тестирования — сервер по умолчанию слушает `127.0.0.1:5000`, и оба клиента по умолчанию указывают этот адрес.

## 8. Сборка релизных сборок

### 8.1 Сервер и классический клиент — self-contained один файл

```bash
./publish.sh              # сразу linux-x64 и win-x64
./publish.sh win-x64       # только один RID
```

Результат оказывается в `release/<rid>/` и упаковывается в `release/LANChat-<rid>.zip`. Эти бинарники несут .NET-рантайм внутри себя — получателю ничего ставить не нужно. Благодаря кросс-паблишу .NET можно собрать `win-x64` прямо с Linux-машины (и наоборот) без какого-либо нативного Windows-тулчейна.

### 8.2 Tauri-клиент — нативный инсталлятор

```bash
cd lanchat-tauri
npm run build
```

В зависимости от хостовой ОС выдаёт: `.AppImage`/`.deb` (Linux), `.msi` (Windows), `.dmg` (macOS) — в `src-tauri/target/release/bundle/`. В отличие от .NET, Rust-бинарники **не кросс-компилируются так же просто** — собирать нужно на целевой платформе (или в CI с соответствующей матрицей ОС) отдельно для каждой.

## 9. Модель безопасности

LANChat изначально спроектирован для **доверенной локальной сети**, а не для открытого интернета.

- **Шифрование транспорта**: каждое соединение использует TLS 1.2/1.3 с самоподписанным сертификатом, генерируемым заново при каждом старте сервера — это защищает от пассивного прослушивания трафика в сети.
- **Отсутствие проверки сертификата**: клиенты намеренно принимают любой сертификат сервера. Это осознанный компромисс — раздавать доверенный CA каждому участнику разового LAN-чата создало бы реальные трудности внедрения почти без практической пользы. Следствие: *активный* злоумышленник, уже находящийся внутри LAN, теоретически мог бы выдать себя за сервер. Если эта угроза критична для вашего сценария использования — в текущем виде проект для этого недостаточен.
- **Подделка отправителя невозможна**: сервер всегда перезаписывает `sender` перед пересылкой.
- **Меры против отказа в обслуживании**:
  - Rate limiting (500 мс между обычными сообщениями; `typing`/`file_chunk` выведены из-под лимита, иначе они были бы бесполезны)
  - Максимальная длина строки протокола, ограничивающая память на одно сообщение
  - Тайм-ауты чтения/записи/хендшейка — простаивающее или зависшее соединение не может держать ресурсы сервера бесконечно
  - Изоляция ошибок по сокетам в цикле рассылки
- **Санитизация ников**: ограничение длины, вырезание запятых (иначе они ломают список онлайн-пользователей, разделённый запятыми).
- **Сознательно не покрыто**: аутентификация (подключиться может кто угодно, у кого есть доступ к TCP-порту и кто подберёт свободный ник), ограничение числа подключений с одного IP, защита от уже присутствующего в LAN активного MITM.

## 10. Траблшутинг и извлечённые уроки

Этот раздел документирует реальные проблемы, найденные и исправленные в ходе разработки проекта — они оставлены как справочный материал, поскольку часть из них — неочевидные особенности платформ, которые вполне могут повториться в похожих проектах.

### 10.1 Повреждённый BOM ломает парсеры файлов

**Симптом:** Avalonia не может собраться с ошибкой `File doesn't contain valid XAML: Data at the root level is invalid. Line 1, position 1`, либо компилятор C# выдаёт лавину бессмысленных синтаксических ошибок начиная с первой строки совершенно корректного `.cs`-файла.

**Причина:** повреждённая или задвоенная метка порядка байтов (BOM) в самом начале файла — обычно появляется при копировании содержимого файла через определённые редакторы, терминалы или менеджеры буфера обмена.

**Решение:** обрезать всё, что стоит до первого реального байта содержимого:
```bash
python3 -c "
content = open('MainWindow.axaml', 'rb').read()
idx = content.find(b'<Window')
with open('MainWindow.axaml', 'wb') as f:
    f.write(content[idx:])
"
```
В сомнительных случаях — пересоздавать файл прямо через heredoc в терминале (`cat > file << 'EOF' ... EOF`), это полностью исключает кодировочные проблемы буфера обмена и редакторов.

### 10.2 События Tauri тихо не доходят

**Симптом:** Tauri-клиент успешно подключается (вызовы `invoke()` отрабатывают), но ни одно сообщение, системное уведомление или обновление списка пользователей никогда не появляется — интерфейс выглядит постоянно пустым.

**Причина:** система разрешений (ACL) в Tauri 2 отдельно регулирует доступ к встроенному плагину `event` (`listen`/`emit`) — в отличие от команд, определённых самим приложением. Команды `#[tauri::command]` под ACL не попадают, поэтому `invoke('connect_to_server', ...)` работал — а вот при полном отсутствии файла `capabilities/default.json` у событийной системы не было вообще никаких разрешений, и каждый `emit()` на стороне Rust тихо отбрасывался.

**Решение:** добавить `src-tauri/capabilities/default.json`:
```json
{
  "identifier": "default",
  "windows": ["main"],
  "permissions": ["core:default", "core:event:default"]
}
```

### 10.3 TLS-хендшейк падает только на Windows

**Симптом:** сервер прекрасно работает между двумя Linux-машинами, но Windows-клиент получает `Received an unexpected EOF or 0 bytes from the transport stream` сразу после успешного UDP-автообнаружения (то есть обнаружение работает, а сам TLS/TCP-коннект — нет).

**Причина:** `CertificateRequest.CreateSelfSigned(...)` возвращает сертификат с **эфемерным** приватным ключом, существующим только в памяти. TLS-стек Windows (SChannel) не умеет использовать такой ключ для серверного хендшейка — ему нужен ключ, привязанный к полноценному контейнеру ключей, — тогда как реализация на базе OpenSSL в Linux спокойно это терпит. Хендшейк падает на стороне сервера, тот закрывает сокет; клиент видит просто обрыв соединения.

**Решение:** прогнать сертификат через экспорт/импорт PFX — это даёт ему ключ, привязанный к хранилищу (неэфемерный):
```csharp
using var ephemeral = request.CreateSelfSigned(DateTimeOffset.Now, DateTimeOffset.Now.AddYears(1));
return X509CertificateLoader.LoadPkcs12(
    ephemeral.Export(X509ContentType.Pfx), null, X509KeyStorageFlags.Exportable);
```

### 10.4 Отсутствие проверки ошибки хендшейка даёт клиенту ложный успех

**Симптом:** пользователь подключается под ником, который уже занят. Сервер корректно отклоняет подключение и закрывает сокет — но интерфейс клиента всё равно показывает «успешно подключено», а любое отправленное после этого сообщение тихо пропадает в никуда.

**Причина:** C#-клиент всегда читал и проверял первую строку ответа сервера на `type: "error"`, прежде чем объявить успех. Команда `connect_to_server` в Rust/Tauri-клиенте этого не делала — она объявляла успех сразу после отправки хендшейка, ни разу не прочитав ответ сервера.

**Решение:** читать одну строку из сокета перед тем, как вернуть успех, и если её `type` равен `"error"` — отдавать это во фронтенд как неудачную попытку подключения; иначе эта же строка пересылается в UI как первое полученное сообщение (обычно это системное уведомление «подключено») перед запуском фонового цикла чтения.

### 10.5 Переподключение без остановки старой фоновой задачи («зомби-подключения»)

**Симптом:** после нескольких переподключений (или отключений и повторных подключений) в рамках одного запущенного процесса клиента входящие рассылки — сообщения чата и особенно многочанковые передачи файлов — начинают приходить задублированными, по разу на каждую предыдущую попытку подключения.

**Причина:** фоновая задача, читающая данные от сервера и генерирующая события `new-message`, никогда явно не останавливалась ни при отключении, ни перед установкой нового соединения — закрывалась только **половина записи** сокета. Задача чтения продолжала работать (а поскольку сервер не обязательно сразу замечал наполовину закрытое соединение, оно оставалось живым зарегистрированным участником), так что каждая следующая рассылка доходила до одного слушателя на каждое накопившееся старое соединение.

**Решение:** сохранять `JoinHandle` задачи и явно вызывать `.abort()` как в `disconnect_server`, так и непосредственно перед запуском новой задачи в `connect_to_server`.

### 10.6 Ловушка «дырявого» массива ломает сборку файлов

**Симптом:** входящие многочанковые файлы от одного типа клиента приходят задублированными — именно по разу на каждый чанк — и никогда не открываются корректно (в каждой «копии» лежит только фрагмент настоящих данных).

**Причина:** буфер чанков создавался через `new Array(totalChunks)`, что даёт *дырявый* (sparse) массив: `totalChunks` незаполненных ячеек, а не `totalChunks` ячеек со значением `undefined`. Метод `Array.prototype.every()` на дырявом массиве тихо пропускает незаполненные ячейки вместо того, чтобы их посетить — поэтому проверка «все ли чанки на месте?» (`chunks.every(c => typeof c === 'string')`) возвращала `true` сразу после прихода первого же чанка, независимо от реального числа чанков в передаче.

**Решение:** `new Array(totalChunks).fill(null)` — заполнение массива делает каждую ячейку настоящим значением, и `.every()` начинает честно посещать и проверять их все.

### 10.7 Скачивание через blob-ссылку тихо не работает внутри WebView

**Симптом:** после исправления п. 10.6 полностью и корректно собранный файл всё равно не открывается по клику на ссылку в Tauri-клиенте.

**Причина:** `<a href="blob:..." download="...">` — это механизм скачивания уровня *браузера*, а встроенный в Tauri WebView (WebKitGTK на Linux, WebView2 на Windows) не всегда надёжно его поддерживает для `blob:`-ссылок — клик может тихо ничего не делать или открывать пустую страницу, в зависимости от платформы и версии WebView.

**Решение:** полностью обойти браузерный механизм скачивания. Декодировать base64 и записать файл на диск напрямую из Rust (команда `save_received_file`), затем открывать его нативным средством ОС (`xdg-open` / `open` / `start`) через команду `open_file`, вместо того чтобы полагаться на какой-либо API скачивания уровня webview.

### 10.8 Лайфтаймы Rust ломают наивные скрипты вырезания комментариев

**Симптом:** общий скрипт «вырезать все комментарии», написанный с расчётом, что каждая одинарная кавычка `'` открывает строку/символьный литерал, портит `.rs`-файлы — всё, что идёт после первой же аннотации лайфтайма (`'a`, `'_`, `'static` и т.п.), поглощается так, будто находится внутри незакрытой строки.

**Причина:** лайфтаймы в Rust используют тот же символ `'`, что и символьные литералы, но, в отличие от символьного литерала, никогда не закрываются парной кавычкой. Токенизатор, не учитывающий этот частный случай, воспринимает кавычку лайфтайма как открытие строки, которая (с его точки зрения) никогда не заканчивается.

**Решение:** прежде чем решить «эта кавычка открывает строку», заглянуть на несколько символов вперёд в поисках правдоподобной закрывающей кавычки (с учётом `\n`, `\\` и экранирования вида `\u{...}`); если поблизости ничего не найдено — считать кавычку обычным символом, а не разделителем строки.

### 10.9 Tauri требует иконку в формате RGBA

**Симптом:** `cargo tauri build`/`dev` падает с ошибкой `proc macro panicked: icon ... is not RGBA`.

**Причина:** обработка иконки на этапе сборки в Tauri требует явного альфа-канала у иконки приложения; обычный RGB (или индексированный по палитре) PNG отклоняется безоговорочно, даже если визуально неотличим от RGBA-варианта.

**Решение:**
```bash
python3 -c "
from PIL import Image
Image.open('icon.png').convert('RGBA').save('icon.png')
"
```

## 11. Частые вопросы

**Можно ли использовать это через интернет, а не только в LAN?**
Без изменений — не рекомендуется. UDP-автообнаружение работает только в пределах одного broadcast-домена, а модель доверия «принимать любой сертификат» (раздел 9) становится реальным риском за пределами сети, которую вы полностью контролируете.

**Зачем поддерживать два отдельных клиента вместо одного?**
У них разные цели — нативное десктопное ощущение против современного веб-интерфейса — и они специально поддерживаются как параллельные, полностью совместимые по протоколу реализации. Это заодно сделало сам протокол куда строже специфицированным: баги, которые особенности одной реализации могли бы маскировать, быстро всплывают, когда с ней должна взаимодействовать вторая, независимая реализация.

**Где хранится история чата?**
Нигде постоянно. Сервер держит последние 50 публичных сообщений в памяти для вновь подключающихся клиентов; перезапуск сервера её стирает. Личные сообщения и файлы не сохраняются вообще, даже временно, дольше момента доставки.
